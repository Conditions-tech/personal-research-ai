# Architecture

Recovery status now distinguishes a failed runtime/model identity probe from low-memory waiting. Each invocation discards stale runtime identity before checking. Safe diagnostic state records the approved loopback endpoint/status and fixed refusal reason without response bodies. Offline regression runs preserve an earlier runtime blocker. Current `/api/tags` is empty under a daemon owned by a different account than the installed model store; [account and manifest reconciliation](C2_QWEN3_RUNTIME_IDENTITY_2026-10-25.md).

`tools/qwen3_recovery.py` wraps the unchanged frozen Qwen3 helper in a kernel job lease, durable worker identity, bounded resource checks and one-case child isolation. The existing ledger remains the only inference meter. A separate empty-request control path can unload only a tracked completed owned model; it never sends analysis or debits the ledger. Unknown workers/models are left alone. The controller performs no daemon restart or self-scheduling; the existing external supervisor may recheck idle waiting work. App routing and saved formats are unchanged. [Recovery design and limitations](C2_QWEN3_RECOVERY_2026-10-25.md).

The approved Qwen3 experiment uses separate `tools/qwen3_pilot.py` and `tools/qwen3_pilot_audit.py`, with pinned new-model identity, versioned 6,144/1,024 CPU/nonthinking settings and its own 5.5 GiB gate/12-attempt ledger. It reuses the frozen v5 source/response contract without changing application routing, legacy globals or saved proposal formats. The original loading gate blocked before inference; actual generation later began after resources qualified. The [live report](C2_QWEN3_LIVE_PILOT_2026-10-21.md) separates metadata, technical operation and field quality. [Pilot boundary](C2_QWEN3_PILOT_2026-10-21.md).

`tools/analysis_adjudication.py` compares reports with exact frozen manifest/case/label bytes. ## Shape

The Streamlit entry point and SQLite functions remain in `app.py`. The importable `discovery` package holds metadata normalization, source adapters and a bounded retrieval controller independently of UI/storage. There is no configuration module, migration runner, model backend, Paper Analyst or Research Strategist yet. ## Discovery boundary

The [second audit](AB_AUDIT_2_2026-10-20.md) added canonical `search_settings` validation before retrieval I/O and captured query/settings snapshots in measured results. Run/history builders check that context, permit one aggregated result per provider, validate insertion counts and reject mismatched attempts. Optional text shapes and abstract positions are validated; nullable name components remain missing values. These changes do not alter the UI, provider request construction, database schema or existing manifest/note versions.

- `discovery/metadata.py`: text/DOI/title keys, abstracts/authors, provider-native category mappings, normalization, and inclusive year/type filtering. Transient dictionaries also retain native source IDs/URLs and venue types for provenance; no paper-table columns were added.
- `discovery/providers.py`: the existing HTTP request function, `OpenAlexAdapter`, `CrossrefAdapter`, the structural `SourceAdapter` protocol, and `SearchBatch`.
- `discovery/retrieval.py`: `RetrievalBudget`, `RetrievalResult`, serial page traversal, partial-result preservation, sanitized errors and structured history notes.
- `discovery/runs.py`: shared run IDs, count/setting manifests, first-nonempty-field merging within a run, version-two history notes, and in-memory ZIP/CSV/JSON exports. No filesystem or database initialization.
- `discovery/__init__.py`: package marker without initialization work.

Both adapters expose `search(query, limit, year_from=None, year_to=None, work_types=None)`. An optional constructor-injected JSON requester takes `(url, params)`; by default it uses the existing requests transport. Constructing or importing an adapter does not request data, create directories, initialize SQLite, or load Streamlit/pandas.

`SearchBatch` separates `reported_total`, its `total_scope`, `fetched_count` (raw response entries, including unusable keys and subsequently excluded records), and `records` after normalization/local filtering. `filtered_count` derives from those records. OpenAlex scope is `server-filtered-candidates`; Crossref scope is `server-filtered-candidates` when any year/type filter is sent, otherwise `query-matches`. A missing provider total stays `None`, never inferred from the batch. Duplicate entries remain in the batch for the existing storage logic. The contract describes one response and makes no completeness claim.

Compatibility functions `search_openalex` and `search_crossref` retain their original single-batch `(reported_total, records)` tuple for existing callers/tests. The UI now calls `retrieve` with adapters' `search_page` contract: OpenAlex basic page numbers and Crossref latest cursors. Raw fetched counts, filtered records, completion status and stop reasons are displayed and included in the existing search-note field. Errors retain earlier pages and are reported without raw exception URLs. No retries are performed.

Either UI year bound is optional. Enabled bounds accept CE years 1-9999, retaining the 2015/current-year defaults. With both off, missing-year records are eligible; a selected type still needs classification evidence. Filtered records also require a usable title/key because the existing persistence function cannot save untitled records. With a known total, final-page completion requires it to remain stable and equal accepted raw counts; both over- and under-count contradictions remain partial. An unknown total stays null and does not prevent a short final page from establishing scoped traversal completion. Title/year shape validation and downstream limits are described in [Phase C Handover](PHASE_C_HANDOVER.md).

The target deployment remains Windows, i3-8100, 8 GB RAM, and integrated graphics with a free/open-source preference. At most 250 entries per source are held during retrieval; no AI model is loaded. Model/provider selection and resource/licence evaluations remain future work.

## Request and storage flow

1. The user supplies a topic, per-provider result limit, year range, and publication types.
2. `retrieve(OpenAlexAdapter(), ...)` requests numbered pages from `https://api.openalex.org/works`, retaining year bounds and native candidate-type filters. Basic paging stays below the provider's depth limit and avoids requiring cursor credentials.
3. `retrieve(CrossrefAdapter(), ...)` sends a bibliographic query with a fixed row size and follows the latest cursor. `crossref_filters` sends `until-pub-date`, a start bound widened by one year, and native `type` filters; exact year/type selection remains local.
4. Both providers' records are normalized into a shared dictionary shape, then passed through `filter_search_results`. Year bounds are inclusive. A missing year is excluded when either bound is set. An empty type selection disables type filtering; otherwise records must have a selected normalized type. OpenAlex abstracts are reconstructed from the inverted index. Crossref abstracts have simple HTML tags removed, but this can leave extra whitespace.
5. Totals retain their provider-specific scope and are never added together. Raw entry/page/time budgets bound traversal; a final page establishes only scoped source completion. Successful earlier pages survive later failures. Returned counts precede deduplication.
6. `save_papers` merges DOI or title/year keys and fills missing fields, including NULL abstract/author/type/URL metadata, without replacing nonempty evidence or first-saved timestamps. Failed batches roll back. New fallback keys distinguish zero from missing year; old keys are not rewritten. `make_run` records new insertions separately from run-unique keys; each `save_search` row gets the same run ID and version-two note. The schema is unchanged; paper/history saves are separate transactions, not an atomic crash-safe run.
7. The UI loads local records, filters title/abstract text, shows selected metadata, and offers the filtered view as a UTF-8-with-BOM CSV download.
8. Search history offers the latest 100 displayed attempts as JSON and this session's latest run ZIP (manifest, run-deduplicated records CSV, provenance CSV). Source IDs, URLs, raw/normalized types, year, venue and page survive in new history notes. Source URLs are record links, not request URLs/cursors. Older history/data are not rewritten, and older run snapshots are not recreated after restart.

The library loader/CSV now includes record_key. Metadata selection uses that key, adding a DOI/key suffix for identical titles, so distinct papers cannot accidentally show the first title match's evidence. Provider years must be integers representable by SQLite (not booleans/floats/strings); unbounded source years are not restricted to the UI's CE entry range. Malformed provider title shapes are rejected as an invalid page.

### Provider-aware publication categories

`PUBLICATION_TYPE_LABELS` defines five search categories. `CROSSREF_TYPE_MAP` maps `journal-article` to `journal-paper`, `proceedings-article` to `conference-paper`, and `book-chapter`, `dissertation`, and `posted-content` to their matching categories. Journal papers deliberately combine articles and reviews; Crossref can include other journal content without a distinct subtype. Peer reviews, unknown types, and missing types are unclassified. The posted-content category is broader than preprints alone.

`openalex_publication_type` accepts explicit native `conference-paper`, `book-chapter`, `dissertation`, and `preprint` types (the latter maps to the shared posted-content category). For the broader `article`/`review` types, only `primary_location.source.type` values `journal` and `conference` establish the corresponding category. Missing locations/sources, other venue types, editorials, book reviews, conference abstracts, and unsupported work types stay unclassified. Titles and venue names are never used to guess types. Native specific work types take precedence over venue metadata.

`OPENALEX_QUERY_TYPES` builds a sorted union of native candidates: journal selection requests `article|review`; conference selection requests `article|conference-paper|review`, allowing both newer native conference labels and older article/review records with explicit conference venues. Other categories request `book-chapter`, `dissertation`, or `preprint`. Crossref-specific `proceedings-article` and `posted-content` are never sent as OpenAlex type filters. Local classification removes candidates outside the selection, so the provider total can exceed matching selected records.

The defaults select journal and conference papers. Clearing the selection removes type filtering while preserving enabled year bounds. The normalized `publication_type` exists in search dictionaries and new provenance notes, not a new paper-table column. Original stored `work_type` values, schema, deduplication keys and old saved records remain unchanged. Provider semantics were checked against official [OpenAlex work types](https://help.openalex.org/data/work-types/), [OpenAlex source types](https://help.openalex.org/data/source-types/), and [Crossref types](https://api.crossref.org/types) on 2026-10-20. OpenAlex's new conference types have limited rollout coverage; venue metadata can also be incomplete or incorrect. Mocked rules and small live examples do not validate corpus classification quality.

Crossref year normalization retains its existing precedence: `published-print`, then `published-online`, then `published`. Filtering uses that normalized year, so an earlier online date does not override an available print date. The filters apply before storage to newly retrieved records; they do not remove or reclassify saved data.

Requests use `requests` with 45-second connect/read inactivity timeouts, a one-second pause between pages and a 0.5-second gap between providers. These are not hard total request deadlines. Calls remain unauthenticated. Search topics are sent to public services; raw errors, cursors and payloads are not copied into history notes. A 429 stops the source, preserves earlier pages and parses numeric/HTTP-date Retry-After into a safe cooldown (default 60 seconds; bounded to one year for malformed extreme values). The UI session skips further requests until its cooldown expires. Multi-session throttling, automatic retries and in-flight cancellation are not implemented.

## Persistence

The subsequent [A/B re-audit](AB_AUDIT_2026-10-20.md) corrected NULL-field enrichment in `save_papers` without changing schema or rewriting production records. Existing nonempty evidence and first-save timestamps remain preserved; a failed paper batch rolls back its inserts/updates. `load_papers` now includes the existing `record_key`, used for stable paper selection and library CSV identity. Identical titles are disambiguated using DOI/key labels. These specific fixes supersede earlier assertions that all storage/helper ASTs were unchanged for prior milestones.

The SQLite database path is resolved relative to `app.py` as `data/research.db`. The app creates the `data/` and `exports/` directories during module initialization. `connect_db` creates `papers` and `searches` tables with `CREATE TABLE IF NOT EXISTS`; this is initialization, not a versioned migration system. Database operations now close their connection after transaction handling. The active app does not write downloaded CSVs into `exports/`.

The `papers` table stores the record key, title, DOI, year, work type, abstract, authors, source names, URL, and first/last-seen timestamps. The `searches` table stores the query, timestamp, provider, reported/retrieved counts, status, and note. Search history displayed by the app is limited to the latest 100 rows.

[Schema Migration Policy](SCHEMA_MIGRATIONS.md) defines future version recognition, staged upgrades, approval, and recovery requirements. It is not implemented: `connect_db` still performs only the existing initialization, with no `user_version` handling or compatibility guard.

## Module and test boundary

The Streamlit interface executes at module scope. Helper tests import discovery normally, but still extract storage/export functions from `app.py` without executing the UI block and point storage at a temporary SQLite file. Separate adapter tests inject/mock provider responses and audit a fresh-process import for side effects. This is not a production plugin loader.

UI smoke tests execute an unchanged copy of the entire application from a temporary directory using Streamlit's `AppTest`. This makes the application's `__file__`-relative data/export paths temporary. Additional guards reject SQLite connections outside the test root and block unmocked HTTP session requests. Synthetic provider payloads exercise the real UI/search/storage flow. No application-level test mode, environment-variable override, or production path change was added. See [Testing](TESTING.md) for coverage and limitations.

The temporary UI script imports the actual workspace's `discovery` package through the test runner's project import path. That package has no data paths or initialization writes; only the script's explicitly temporary storage is opened. Copying `app.py` alone is no longer a standalone application distribution.

The backup rehearsal separately extracts only `connect_db` to create temporary app-schema fixtures. It tests the Python workflow definitions in `docs/DATA_AND_BACKUP.md`, including staged replacement and rollback entirely inside a disposable directory. There is no backup/restore feature in the application and no automatic production replacement.

## Known boundaries

- Venue and native source identifiers are available in new run provenance/history notes, but the unchanged paper table/library view does not store them as separate columns.
- Provider metadata and count semantics differ; counts must not be added together as a global total. Crossref's total is before exact local filters, and its bounded response can produce fewer filtered records than the configured maximum.
- No full-text retrieval, citation graph, query expansion, ranking, or AI-generated analysis exists in the audited implementation.
